# 概述

微子按角色划分你的机器。中枢负责网络并发布服务，被控端提供这些服务，客户端使用它们。本页说明每个角色在你的网络里的位置，并跟着一项服务，从提供它的机器一直走到客户端里的按钮。

## 中枢的各层

中枢在 Linux 上可以用任何网络形态运行，在 macOS 和 Windows 上以服务器形态运行。中枢所在的机器按下表的顺序分层。每一层只依赖它前面的层，后三层在服务器形态下都能用。

| 层       | 是什么                                                                                                                                                                 | 关闭时                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 网络形态 | 这台机器在你的网络里的位置。**服务器**（Server）不做路由；**旁路网关**（Side gateway）为把它设成网关的主机转发；**路由器**（Router）在上行网口和它服务的网络之间路由。 | 每台机器都有一种形态；服务器形态保持原有网络不变。 |
| 外部访问 | 从外面连回来的办法：用 NetBird 或 EasyTier 组的跨互联网私网，或你自己服务器上的中继。外面的机器经其中任意一种访问这台机器。                                            | 只有本地网络里的机器能访问这台机器。               |
| 代理     | 一个 xray 进程，出口节点从分享链接导入。它接管这台机器自己的流量和 SOCKS 端口；在路由形态下，也接管背后设备的流量。                                                    | 所有连接都从这台机器自己的上行出去。               |
| AI 网关  | 一个入口，默认端口 8317，背后是 API 密钥和订阅账号。每个客户端有自己的密钥和用量统计。                                                                                 | 每个 AI 工具保持各自原来的配置。                   |

![中枢居中，经虚拟网访问，驱动被控端、AI 网关、存储和服务](/guide/architecture_zh.svg)

只有路由器形态会接管这台机器的网口，并提供它自己的网络。服务器和旁路网关形态下，这台机器上的每个地址、每个连接都保持原样。各种形态和切换方法见[网络](./hub/network.md)。

两个虚拟网引擎同时开着时，中枢让它们的网段互不重叠。一个引擎的网段与另一个引擎或这台机器自己的网段重叠时，中枢拒绝启动它，返回 `overlay_subnet_overlap`。虚拟网推来默认路由时，中枢删除这条路由，并在页面上显示 `overlay_default_route_refused`。每个引擎的设置见[外部访问](./hub/overlay.md)。

## 提供者与使用者

每个模块都在一个被控端下运行，装在具备所需条件的机器上：共享要有硬盘，Gitea 要有仓库，容器要有显卡。Linux 机器能运行所有模块。Windows 和 Mac 用系统自带的 SMB 服务器提供共享，另外能运行 VS Code、CloudCLI 和共享桌面；Mac 还能运行 code-server。完整的对照表见[支持的平台](./reference/platforms.md)。

客户端使用这些机器提供的东西：打开网页，转发端口，让 AI 工具指向网关，挂载共享，连接桌面，打开终端。`nhub setup` 在中枢自己的机器上也装了被控端，所以这台机器和其他受管机器一样能提供模块。AI 网关是中枢自己提供的唯一一项服务。

客户端用的每一项服务都经中枢连过去。客户端在自己的回环地址上开一个端口，连到这个端口的每条连接，都变成一条去中枢 8443 端口的流。中枢把这条流交给提供服务那台机器的被控端，被控端再在本机回环上连到服务。AI 网关和手动声明的服务，由中枢自己去连。所以客户端只要连得上中枢的一个地址就行，在局域网里直接连，在外面经[外部访问](./hub/overlay.md)里的办法连，不需要通往那台机器的路由。

面板侧栏按同样的方式分组。**中枢** 组从**总览**（Dashboard）到**设置**（Settings），作用在这台机器上。**被控端**（Agent）组包括**终端**（Terminals）、**文件**（Files）和**模块**（Modules），每次作用在一台受管机器上。

## 从机器到按钮

客户端收到的服务来自模块、手动声明或机器本身：

- 模块发布自己的条目。共享模块发布每个共享，Gitea 发布它的地址，VS Code、code-server 和 CloudCLI 发布每个实例，容器发布它映射出来的每个主机端口。
- **服务**（Services）页发布你手动声明的条目：一个网址、一个 TCP 端口，或一台不归中枢管理的服务器上的 SMB 共享。
- 模块页上这台机器的 **Remote desktop** 开关打开时，这台机器自己上报它共享的桌面。

每个条目有一个类别。客户端为每个类别显示一个面板，每个条目旁边有一个按钮：

| 面板                            | 由谁发布                                            | 客户端的按钮                                                                           |
| ------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **网页**（Web）                 | Gitea、VS Code、code-server、CloudCLI，或声明的网址 | **打开**（Open），把条目转发到 `127.0.0.1` 并在浏览器里打开                            |
| **端口**（Ports）               | 容器映射的端口，或声明的 TCP 端口                   | **连接**（Connect），把端口转发到 `127.0.0.1`                                          |
| **AI**                          | AI 网关                                             | **配置**（Configure），以及开关 **AI 工具使用此网关**（The AI tools use this gateway） |
| **文件**（Files）               | 共享模块，或声明的 SMB 共享                         | **配置**，然后**挂载**（Mount）                                                        |
| **远程桌面**（Remote desktops） | 机器自己的被控端                                    | **连接**                                                                               |

**终端**（Terminals）面板列出这个客户端可以开 shell 的受管机器，**新终端**（New terminal）打开一个。中枢只把**客户端**（Clients）页上权限允许的类别和机器发给每个客户端。中枢发布的全部条目见[服务](./hub/services.md)，每个面板的用法见[桌面客户端](./client/desktop.md)。

## 安装包与协议 3

同一个发布 tag 一起发布中枢、被控端和客户端的包：

| 包                | 装在哪                                                                          | 以什么身份运行                                             |
| ----------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `neutrino-hub`    | 一台机器：x86-64 或 ARM64 的 Linux，任何网络形态；或服务器形态的 macOS、Windows | root，作为面板和它的各个服务单元；Windows 上是 LocalSystem |
| `neutrino-agent`  | 每台受管机器：Linux、Windows 10 或 11、Apple 芯片或 Intel 的 macOS              | root 服务，Windows 上是 LocalSystem，没有窗口              |
| `neutrino-client` | 每个人的 Linux、Windows 或 macOS 电脑                                           | 这个人自己的账户                                           |

Android 应用是同一个发布里单独的 apk。这些包之间要对上的是协议号，0.5.0 的每个包都讲协议 3。0.5.0 的中枢接受协议号在 `PROTOCOL_MIN` 到 `PROTOCOL` 之间的对端，两者都是 3。范围之外的对端，中枢返回 `protocol_too_old` 或 `protocol_too_new`。对端保留绑定，一分钟后重新连接。协议号在范围内的被控端，在中枢给出更新的版本时自行升级。

0.3 或 0.4 的被控端和客户端讲协议 1 或 2，0.5.0 的中枢对它们返回 `protocol_too_old`。这样的对端也不会自行升级。中枢升级时会重装它自己机器上的被控端，其余的被控端由你重装。升级顺序见[设置](./hub/settings.md)，中枢最先；改协议号的规则见[通道](./protocol/channel.md)。
