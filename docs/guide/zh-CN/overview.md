# 概述

微子把你的机器分成三个角色。中枢管网络，并把服务发布出去；被控端装在提供服务的机器上；客户端装在使用服务的电脑或手机上。本页顺着一项服务，从提供它的机器一路走到客户端里的按钮，说明每个角色在你网络里的位置。

## 中枢的各层

Linux 上的中枢有三种网络形态：服务器、旁路网关和路由器，路由器还有只用一根网线的单臂变体。macOS 和 Windows 上的中枢只有服务器形态。不管哪种形态，中枢所在的机器都按下表分层：

| 层       | 是什么                                                                   | 关掉时                               |
| -------- | ------------------------------------------------------------------------ | ------------------------------------ |
| 网络形态 | 这台机器在你网络里的位置；服务器形态不做路由，另外两种为别的设备转发流量 | 不能关；服务器形态让原有网络保持原样 |
| 外部访问 | 从外面连回中枢的办法：直连、SSH 中继、NetBird、EasyTier                  | 只有同一个局域网里的设备连得到中枢   |
| 代理     | 一个 xray 进程，按规则把流量交给出口节点；只在完整版里有                 | 所有连接都从这台机器自己的上行出去   |
| AI 网关  | 一个入口，背后是 API 密钥和订阅账号，每个客户端有自己的密钥和用量        | 每个 AI 工具保持它原来的配置         |

![中枢居中，经外部访问连到客户端，管理被控端、AI 网关和服务](/guide/architecture_zh.svg)

只有路由器形态接管这台机器的网口，自己提供一个网络。服务器和旁路网关形态下，这台机器原有的地址和连接都保持不变。每种形态是什么、怎么切换，见[网络](./hub/network.md)。

## 提供者与使用者

模块装在具备它所需资源的机器上，例如文件共享装在有硬盘的机器上。Linux 机器能运行全部模块。Windows 和 Mac 能运行文件共享、终端、远程桌面、Gitea、VS Code 和 CloudCLI，Mac 还能运行 code-server；容器和 ZFS 存储只有 Linux 版。每个系统的完整对照见[支持的平台](./reference/platforms.md)。

`nhub setup` 在中枢自己那台机器上也装了被控端。所以这台机器和其他受管机器一样，能提供模块。

客户端用到的每条连接，都经中枢的 8443 端口转发。客户端在本机回环地址上开一个端口，连到这个端口的连接变成一条去中枢的流。中枢再把这条流交给提供服务那台机器的被控端。因此客户端只需要中枢的一个地址，不需要通往每台机器的路由。

面板侧栏也按这两种角色分组。**中枢**（Hub）组里的页面作用在中枢这台机器上。**被控端**（Agent）组里的**终端**（Terminals）、**文件**（Files）和**模块**（Modules），每次作用在一台受管机器上。

## 从机器到按钮

客户端看到的每个条目，来源是下面之一：

- 模块发布的条目：每个文件共享、Gitea 的网址、每个 VS Code 或 code-server 实例、每个容器映射出的端口。
- **服务**（Services）页上手动声明的条目：一个网址、一个 TCP 端口，或一台没归中枢管理的服务器上的 SMB 共享。
- 机器自己上报的桌面：面板 **模块**（Modules）页上这台机器的 **Remote desktop** 标签里，共享开关打开之后才有。

每个条目属于一个种类。客户端为每个种类开一页，每个条目旁边是一个按钮：

| 客户端的页                      | 条目从哪来                                          | 条目旁的按钮                                                |
| ------------------------------- | --------------------------------------------------- | ----------------------------------------------------------- |
| **网页**（Web）                 | Gitea、VS Code、code-server、CloudCLI，或声明的网址 | **打开**（Open），在本机浏览器里打开                        |
| **端口**（Ports）               | 容器映射的端口，或声明的 TCP 端口                   | **连接**（Connect），把端口转发到 `127.0.0.1`               |
| **AI**                          | 中枢的 AI 网关                                      | 开关 **AI 工具使用此网关**（The AI tools use this gateway） |
| **文件**（Files）               | 文件共享模块，或声明的 SMB 共享                     | 先选 **配置**（Configure），再选 **挂载**（Mount）          |
| **远程桌面**（Remote desktops） | 打开了远程桌面开关的机器                            | **连接**，打开查看器                                        |

客户端的 **终端** 页列出它能开 shell 的受管机器。中枢发给每个客户端的，只有 **客户端**（Clients）页上权限允许的种类和机器。中枢发布的全部条目见[服务](./hub/services.md)。

## 安装包与协议 3

同一个发布标签同时发布中枢、被控端和客户端三种安装包，以及 Android 应用：

| 安装包            | 装在哪                                                        | 以谁的身份运行                           |
| ----------------- | ------------------------------------------------------------- | ---------------------------------------- |
| `neutrino-hub`    | 一台常开的机器：Linux 任意形态，或服务器形态的 macOS、Windows | root；Windows 上是 LocalSystem           |
| `neutrino-agent`  | 每台受管的 Linux、Windows 或 Mac                              | root，没有窗口；Windows 上是 LocalSystem |
| `neutrino-client` | 每个人自己的 Linux、Windows 或 Mac 电脑                       | 这个人自己的账户                         |
| Android 应用      | 每个人的 Android 手机                                         | 手机上的这个应用                         |

这些包之间要对上的是协议号。0.5.0 的每个包都讲协议 3，中枢只接受协议 3 的对端。0.3 和 0.4 的被控端和客户端讲更早的协议，0.5.0 的中枢拒绝它们，返回 `protocol_too_old`。

0.4 的中枢不能升级到 0.5.0。删掉 0.4 的中枢，全新安装 0.5.0，再用新的链接让被控端和客户端重新加入。具体做法见[设置](./hub/settings.md)。
