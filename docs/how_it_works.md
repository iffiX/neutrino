# 工作原理

你的设备只连接中枢的一个端口，中枢检查权限后连接应用。

![客户端、手机 App 和被控端用 Noise 连接中枢的同一个端口，浏览器访客用 WebRTC 连接这个端口](/guide/zh/security_topology.svg)

协议、防扫描和防 DoS 的细节见[安全模型](/share/security)。

## 组成部分

| 部分   | 运行位置                                  | 作用                                                           |
| ------ | ----------------------------------------- | -------------------------------------------------------------- |
| 中枢   | 你选择的一台 Windows、macOS 或 Linux 电脑 | 提供网页面板，保管凭据，监听连接端口，检查权限，转发连接       |
| 被控端 | 每个加入中枢的系统，包括中枢所在的系统    | 安装和运行应用，上报状态。它主动连接中枢，不为中枢开放任何端口 |
| 客户端 | 你的电脑和手机                            | 连接中枢，列出你有权限使用的应用，在本机打开地址并转发到应用   |

面板和中枢的配置都保存在中枢上。面板上的每个改动先写入配置，再生成各个程序的设置，最后才生效，所以备份配置目录就能恢复整个中枢。

## 连接过程

下面以手机打开电脑上的 CloudCLI 为例。

1. 手机同时连接中枢的所有地址，包括局域网地址和你开启的每种外部访问。手机保留最先完成握手的线路，所以网络变化时会自动切换线路。
1. 中枢先检查连接开头的字节。字节不符时，中枢不回应这条连接，所以扫描器无法识别服务。
1. 检查通过后，手机和中枢完成一次 Noise 握手。手机用加入链接里的公钥验证中枢，中枢用保存的记录验证手机。第三方线路只能看到密文。
1. 握手之后，这条 TCP 连接用 yamux 复用多条流。网页、端口、终端、文件和远程桌面，每次使用都是一条新的流。
1. 你在 **应用** 页按 **使用**，手机在本机打开一个地址，只有手机自身能访问这个地址。每个入口的本机端口是固定的，所以书签一直有效。
1. 你按 **打开**，浏览器访问这个地址。手机打开一条流到中枢，中枢检查这台手机有没有这个应用的权限。
1. 中枢连接应用所在的系统。被控端的转发器核对令牌后，代为登录应用，所以你不用输入密码。

无论设备在局域网还是外部网络，中枢都转发每一条流。所以连接只有一条路径，也只需要一套权限检查。

## 连接方式

所有连接方式到达的都是同一个连接端口，区别只是到达端口的路径。

| 连接方式           | 到达端口的路径                                             | 需要的条件                     |
| ------------------ | ---------------------------------------------------------- | ------------------------------ |
| 局域网             | 设备直接连接中枢的局域网地址                               | 设备和中枢在同一个网络         |
| 直连               | 路由器把公网地址的端口转发到中枢                           | 宽带有公网地址                 |
| SSH 中继           | 中枢用 SSH 连接你的 VPS，VPS 把一个端口转发到中枢          | 一台你自己的 VPS               |
| SakuraFrp、OpenFrp | 中枢运行 frpc 连接服务商的节点，节点转发连接               | 一个账号                       |
| NetBird、EasyTier  | 中枢和设备加入同一张虚拟网，设备再连接中枢在虚拟网里的地址 | 一个账号，或者自己填写引导节点 |

无论使用哪种连接方式，加密的两端都是设备和中枢，所以经过的服务器无法读取内容。

## 应用分享的连接过程

访客的浏览器没有客户端，所以使用另一条路径，连接的还是同一个端口。

1. 访客打开链接，浏览器从分享站加载静态页面。链接里 `#` 后面的内容不会发给这个网站。
1. 页面从 `#` 后面读取中枢的地址和证书指纹，再用浏览器的 WebRTC 连接中枢。
1. 中枢读取连接开头的字节，识别出 STUN 后选择访客路径。浏览器按指纹验证中枢，双方建立 DTLS 加密，再打开数据通道。
1. 页面把应用的网页请求都写入这个数据通道，中枢再转发给应用。访客只能打开这一个应用。

分享站只提供页面文件，不处理任何内容。你也可以换成自行部署的站点。

## 使用的技术

| 用途               | 技术                                                          |
| ------------------ | ------------------------------------------------------------- |
| 设备和中枢的加密   | Noise 协议                                                    |
| 一条连接上的多条流 | go-yamux                                                      |
| 浏览器访客的连接   | WebRTC（STUN、DTLS、SCTP），用 pion 实现                      |
| 连接层             | Go，中枢、被控端和三个客户端使用同一份代码                    |
| 中枢和被控端       | Python，面板使用 FastAPI 和 React                             |
| 手机 App           | Android 使用 Kotlin，iOS 使用 Swift                           |
| 远程桌面           | RustDesk                                                      |
| 文件共享           | Linux 上使用 Samba，Windows 和 macOS 上使用系统自带的共享服务 |
| 容器               | Podman，Windows 上经过 WSL 2，macOS 上经过 Podman 虚拟机      |
| 外部访问           | NetBird、EasyTier、OpenSSH、frpc                              |
| AI 网关            | CLIProxyAPI                                                   |

## 部分组件停止时的影响

| 停止的部分         | 影响                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| 中枢所在的电脑关机 | 客户端和分享链接都无法连接。其他系统上的应用继续运行，中枢开机后可以再次访问 |
| 某个系统离线       | 这个系统上的应用暂时打不开，其他系统不受影响。系统恢复后，应用可以再次打开   |
| 一种外部访问中断   | 客户端在网络变化或重新连接时，自动使用其他已开启的线路                       |
| 分享站打不开       | 新打开的分享链接要等分享站恢复，你也可以换成自行部署的站点                   |
