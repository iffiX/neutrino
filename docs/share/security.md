# 安全模型

微子·中枢的所有外部连接都经过一个 TCP 端口，默认是 8443。持有加入链接的设备用 Noise 协议连接这个端口，持有分享链接的浏览器用 WebRTC 连接这个端口，其他连接收不到任何数据。

## 快速回答

| 问题                             | 回答                                                                                                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 谁能连接这个端口                 | 打开 **直连**、SSH 中继、SakuraFrp 或 OpenFrp 后，互联网上的任何主机都能建立 TCP 连接。只有持有链接的连接能通过检查。                                                   |
| 没有链接的人能看到什么           | 中枢不向这些连接发送任何数据，保持一段随机时间后重置连接。扫描器只能探测到端口开放，无法识别服务。                                                                      |
| 别人能注册或加入吗               | 中枢没有注册功能。设备必须使用你在面板上生成的加入链接，链接 30 分钟内有效，只能使用一次。                                                                              |
| 第三方服务器能读取内容吗         | 不能。经过 SakuraFrp、OpenFrp、NetBird、EasyTier 或你的 VPS 时，加密的两端仍然是设备和中枢。连接的通断和速度由这些服务器和线路决定。                                    |
| 分享链接外泄了怎么办             | 持有链接的人都能打开这个应用，直到分享结束。链接不限人数，也不记录访客身份。发现外泄后按 **撤销**，连接立即断开。                                                       |
| 分享链接能打开什么               | 只能打开分享的这一个应用，不能打开面板、终端或文件。但是访客在应用里能做的事由应用决定。code-server 有终端，所以访客能访问运行账户能访问的所有文件。                    |
| 应用有漏洞时，陌生人能利用吗     | 经连接端口不能。没有授权的客户端看不到这个应用，也打不开它。只有你授权的客户端或分享链接遭到滥用时，别人才能接触到应用的漏洞。范围见[应用不直接暴露](#应用不直接暴露)。 |
| 手机丢了怎么办                   | 到 **客户端** 页停用这台设备，中枢立即关闭它的连接。**免密码进入中枢面板** 默认关闭，只给你自己的设备打开。                                                             |
| 这台电脑上的其他程序能访问应用吗 | 客户端的转发监听 `127.0.0.1`，所以这台电脑上的程序都能连接。网页入口有自己的令牌，端口入口没有。                                                                        |

### 这些回答成立的前提

- 中枢所在的电脑由你管理。这台电脑的管理员能解开保险库，见[数据和外连](/hub/what_it_holds)。
- 面板密码只有你知道。加入链接和分享链接都只有登录面板的人能生成。
- 你只把链接发给你要发的人。
- 访客的浏览器加载的页面来自你选择的站点，默认是 `share.neutrinohub.net`。这个网站只提供静态页面，你也可以[自行部署](/share/web_share)。

### 不保护的情况

- **授权客户端或分享链接遭到滥用：** 中枢检查谁能打开应用，不检查应用里面的操作。如果有人滥用你授权的客户端或分享链接，就能接触到应用自身的漏洞。所以你只授权需要的应用，及时停用不再使用的客户端，撤销不再使用的分享。
- **他人控制了中枢所在的电脑：** 这台电脑的 root 能读取保险库，也能看到经过的内容，因为每条连接都在中枢解密后再转发。
- **手动添加的子网路由：** 这种路由能访问网段上每台设备的每个端口，不经过中枢的权限检查。
- **占满线路的流量攻击：** 中枢的限制保护自身的 CPU 和内存，不能增加线路的带宽。

## 技术架构

### 连接拓扑

![客户端、手机 App 和被控端用 Noise 连接中枢的同一个端口，浏览器访客用 WebRTC 连接这个端口](/guide/zh/security_topology.svg)

连接层是 Go 模块 `transport/`，它在不同位置的运行方式如下。

| 位置               | 运行方式                                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 中枢               | 独立进程 `neutrino_transport`，持有连接端口。Linux 上以系统账户 `neutrino_transport` 运行，不是 root；macOS 和 Windows 上以 root 或 SYSTEM 运行 |
| 被控端、桌面客户端 | Python 程序启动的子进程                                                                                                                         |
| Android、iOS       | 同一份 Go 代码，以库的形式嵌入 App                                                                                                              |
| 浏览器访客         | 不运行 Go 代码。分享页是纯 JavaScript，压缩后不到 40 KB，连接由浏览器自带的 WebRTC 完成                                                         |

每个设备只保持一条到中枢的 TCP 连接。被控端主动连接中枢，所以被控端所在的系统不用为中枢开放端口，也可以位于 NAT 后面。

设备同时连接中枢的所有地址，保留最先完成握手的连接。

Go 进程只负责传输字节，权限、票据和绑定都由 Python 管理。两者之间是本地通道，Linux 和 macOS 上是 Unix 套接字，Windows 上是命名管道。Go 进程在会话建立时询问一次，每条流打开时询问一次，传输字节时不询问。Python 没有及时回答时，中枢拒绝新的连接，已经打开的流不受影响。

### 8443 怎么分流

连接端口不是先建立一种协议再切换到另一种。中枢读取每条连接的首字节，然后选择路径。

![连接端口按首字节选择成员路径、访客路径或拒绝，通过校验之前中枢不写任何字节](/guide/zh/security_door.svg)

| 连接开头的字节       | 路径                         | 来源                                  |
| -------------------- | ---------------------------- | ------------------------------------- |
| 这个中枢的魔数       | 成员路径：敲门、Noise、yamux | 客户端和被控端                        |
| STUN Binding Request | 访客路径：DTLS、SCTP、yamux  | 浏览器，并且有生效的分享              |
| 其他                 | 拒绝                         | 扫描器、错误的客户端、0.5 的 TLS 连接 |

魔数由中枢的静态公钥派生，每个中枢不同。魔数的开头和 STUN、TLS 都不同，所以中枢读到开头的字节就能区分路径。

浏览器走另一条路径，原因是网页不能打开原始 TCP 连接。`wss://` 遇到自签名证书时无法继续，`https` 页面里的 `ws://` 会作为混合内容遭到拦截。WebRTC 的 DTLS 信任页面给出的证书指纹，所以不需要域名和证书颁发机构。

访客路径没有信令服务器。分享页从链接 `#` 后面读取中枢的 IP 地址、端口、证书指纹、ufrag、pwd 和票据，自己写出中枢一侧的会话描述。浏览器不会把 `#` 后面的内容发给网站。中枢是 ICE-lite，只提供一个 TCP 被动候选，也就是连接端口，所以丢弃 UDP 的网络、SSH 中继和 frp 隧道都能承载分享。

把敲门、Noise 和 yamux 编译成 WebAssembly 后，压缩大小是 1.7 MB。分享页优先保证加载速度，所以访客路径用浏览器自带的 DTLS 加密，再用分享的票据证明访问权。

### 成员路径的敲门和握手

成员路径的 Noise 模式和 WireGuard 相同，是 `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`，并采用同样的 mac1、mac2 和 cookie 机制。区别是它运行在 TCP 上，因为局域网、SSH 中继、frp 隧道和虚拟网都能传输 TCP。

设备连接后先发送敲门报文。中枢依次检查报文里的魔数和 mac1，全部通过后才执行 Diffie-Hellman 运算。mac1 需要中枢的公钥，而公钥只存在于加入链接里，所以没有链接的发送方在这一步就会失败。

握手用到下面这些凭据。

| 凭据         | 内容                                  | 有效期                    | 中枢保存                        |
| ------------ | ------------------------------------- | ------------------------- | ------------------------------- |
| 中枢静态密钥 | Curve25519 密钥对，公钥在加入链接里   | 直到执行 `nhub reset all` | 私钥只有传输进程使用            |
| 票据         | 随机生成，在加入链接里                | 30 分钟，只能使用一次     | SHA-256                         |
| 设备静态密钥 | Curve25519 密钥对，设备读取链接时生成 | 直到设备离开或绑定删除    | 公钥                            |
| 令牌         | 随机生成，加入成功后返回              | 和绑定相同                | SHA-256，作为之后每次握手的 PSK |

每次握手都要同时证明设备的静态私钥和令牌。中枢保存的公钥和令牌哈希不足以冒充设备，因为设备的私钥只在设备的绑定文件里。设备用链接里的公钥验证中枢，所以冒充中枢的服务器无法完成握手。

敲门报文的加密部分带有时间戳。中枢为每个设备公钥记录最新的时间戳，不比它新的敲门会遭到拒绝，所以重放抓到的敲门得不到回应。每次握手使用新的临时密钥，所以旧流量不会因为长期私钥泄露而解密。一个会话在结束之前不更换密钥。

### 防扫描

| 机制                                               | 作用                                              |
| -------------------------------------------------- | ------------------------------------------------- |
| 通过 mac1 或分享的 HMAC 校验之前，中枢不写任何字节 | 没有链接的发送方只能看到 TCP 自身的报文           |
| 每条连接随机读取一定数量的字节后才判定拒绝         | 无法根据断开的位置逐字节猜出魔数                  |
| 每条连接随机保持一段时间后才重置                   | 无法根据时间区分魔数错误、mac1 错误和访客路径关闭 |
| 总是用 RST 关闭                                    | 无法根据 RST 或 FIN 判断是否还有未读数据          |
| 敲门和回答加随机长度的填充                         | 没有固定的包长特征                                |
| 没有生效的分享时，访客路径关闭                     | 没有分享时，STUN 连接和其他错误连接反应相同       |

在实验机上，中枢对空连接、随机字节、HTTP、TLS 握手、错误的敲门和对不上分享的 STUN 都没有回复任何数据。抓包结果里没有带内容的数据包，nmap 只能按端口号猜测服务。

### 防 DoS

下面的限制作用于整个端口，不按来源地址计算，因为经过 SSH 中继和 frp 时，所有连接都来自回环地址。

| 消耗的资源    | 限制                                                                    | 达到限制时                                                                  |
| ------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 连接名额      | 未准入的连接有总数上限                                                  | 依次关闭正在保持的已拒绝连接、最旧的未完成握手连接、最旧的连接              |
| 内存          | 保持中的连接只占读取首字节的缓冲区；中枢不再读取，发送方由 TCP 流控停住 | 每条连接最多占一个内核接收缓冲区                                            |
| CPU           | mac1 通过后才执行 DH；同时进行的握手有上限                              | 新连接立即关闭，不写任何字节                                                |
| CPU，负载高时 | 进行中的敲门过多时，要求有效的 mac2                                     | 发送 cookie 回复并关闭。发送方要证明能读到中枢写给它的数据，cookie 定期失效 |
| 准入时间      | 握手和整个准入都有时限                                                  | 关闭连接                                                                    |
| 加入票据      | 短时间内错误凭据过多                                                    | 暂停新的加入，已绑定的设备照常连接                                          |
| 已准入的会话  | 会话数和每个会话的流数都有上限                                          | 拒绝新会话或新流                                                            |
| 流的内存      | 单条流的窗口和所有流的总内存都有上限                                    | 窗口不再增长，发送方等待                                                    |
| 帧大小        | 控制帧和记录都有大小上限                                                | 结束会话或重置流                                                            |

扫描和洪水攻击不会计入加入失败，因为超时、错误的敲门和格式错误都不算错误凭据。所以这类流量不会暂停你的新设备加入。

坏连接占满名额时，实测真实被控端不到 1 秒完成加入。没有链接的发送方收不到中枢的回包，所以这条路径没有流量放大。

### 数据怎么转发

下面以一个网页应用为例。图中的编号对应下面的步骤。

![应用的数据经过客户端的 yamux 流到达中枢，中枢检查权限后把它和被控端上的另一条流拼接起来](/guide/zh/security_relay.svg)

1. 浏览器连接客户端监听的 `127.0.0.1:<本机端口>`。
1. 客户端的传输层在现有会话上打开一条 yamux 流，第一条记录是 `open {kind: connect, id}`。`id` 是应用的条目 ID，不是地址。
1. 中枢的传输层询问 Python。Python 按这台设备的权限检查类型、系统和条目，从中枢自己的记录里取出目标。
1. 中枢在目标系统的被控端会话上打开另一条流。
1. 被控端确认这个端口已发布，再连接 `127.0.0.1:<应用端口>`。没有发布的端口会遭到拒绝，所以中枢的检查出错时也打不开其他端口。
1. 两边都接受后，中枢的传输层在两条流之间复制字节，不再询问 Python。
1. 访客的请求走同一个转发过程。应用页面的请求经 Service Worker 交给 `shell.js`，`shell.js` 把它写成 HTTP/1.1，放进数据通道里的 `connect` 流。访客会话只能打开分享的条目，`shell`、`exec`、`file` 这类流会直接关闭。

设备到中枢、中枢到被控端是两段独立的加密，中枢解密后再转发。这样在家和在外面都只有一条路径，也只有一套权限检查。

收回权限时，中枢立即关闭这个权限覆盖的流和会话。下一条流按新的权限检查，不用重新连接。

所有流共用一条 TCP 连接，所以有两个代价：

- 丢包时，这条连接上的所有流都要等待重传。
- 往返 100 毫秒时，3 KB 请求在空闲会话上需要 102 毫秒，文件拷贝期间需要 200 毫秒，最多 300 毫秒。

### 应用不直接暴露

微子·中枢的设计目的之一是让应用不直接暴露在网络上。打开外部访问后，应用的漏洞不会因此暴露给陌生人，依据如下：

- **对外只有连接端口：** 外部访问只把连接端口开放给外部网络，面板和应用的端口不开放。
- **没有授权就看不到：** 中枢发给客户端的状态只包含权限允许的应用，所以没有授权的客户端的 **应用** 页里没有这个应用。
- **没有授权就打不开：** 客户端直接请求这个应用的条目时，中枢按权限检查后拒绝。
- **应用只监听本机：** 微子·中枢部署的网页应用只监听 `127.0.0.1`，由被控端的转发访问。
- **分享链接只到一个应用：** 持有分享链接的访客只能打开分享的这个应用。

下面这些不经过连接端口，不在这个保护范围内：

- **你声明的服务：** 这些服务监听它们自己的地址，同一网络的设备可以直接连接，依靠它们自己的登录。
- **Linux 上绑定到局域网地址的容器端口：** 同一网络的设备可以直接连接。
- **Windows 和 macOS 上的文件共享：** 它使用系统自带的 SMB 服务，同一网络的设备可以直接连接，依靠账户登录。
- **系统上你自己运行的其他服务：** 这些服务是否对外开放，由系统防火墙决定。

### 协议 4 和协议 3

0.6.0 使用协议 4，0.5.2 使用协议 3。两者不兼容，0.5 的设备连接 0.6 的中枢时收不到任何数据，所以升级时要重新加入，见[从 0.5 升级](/hub/upgrade)。

| 项目         | 协议 3（0.5.2）                             | 协议 4（0.6.0）                        |
| ------------ | ------------------------------------------- | -------------------------------------- |
| 中枢上的进程 | 面板的 Python 进程                          | 独立的 Go 进程，Linux 上不以 root 运行 |
| 加密         | TLS 1.2 或更高版本                          | Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s  |
| 验证中枢     | 钉住证书的 SHA-256 指纹                     | 链接里的静态公钥                       |
| 验证设备     | 连接建立后在 `hello` 里发送令牌             | 握手同时证明静态私钥和令牌             |
| 收到扫描时   | 任何人都能完成 TLS 握手，扫描服务能收录证书 | 不写任何字节                           |
| 多条流       | 一条 WebSocket，二进制帧开头是 4 字节流 ID  | go-yamux                               |
| 单条流的窗口 | 固定 1 MiB                                  | 随往返时间增长                         |
| 浏览器访客   | 不支持                                      | WebRTC                                 |

实测结果如下。

| 项目                                        | 协议 3                  | 协议 4                   |
| ------------------------------------------- | ----------------------- | ------------------------ |
| SMB 下载，往返 100 毫秒                     | 4.7 MB/s                | 25.8 MB/s                |
| SMB 上传，往返 100 毫秒                     | 4.9 MB/s                | 26.4 MB/s                |
| SMB 下载，局域网                            | 243 MB/s                | 433 MB/s                 |
| 中枢每传输 1 GiB 的 CPU 时间，往返 100 毫秒 | 5.5 秒                  | 2.1 到 2.8 秒            |
| code-server 冷启动首屏，往返 100 毫秒       | 5.85 秒                 | 2.84 秒                  |
| 中枢内存                                    | 137 MiB（整个面板进程） | 12 到 15 MiB（传输进程） |

测试环境是同一台主机上的三台虚拟机，分别运行客户端、中枢和被控端，每台 4 核 4 GiB，系统是 Ubuntu 22.04。测试内容是 2 GiB SMB 拷贝，取 3 次的中位数，往返延迟用 netem 模拟。协议 3 一列使用和 0.5.2 相同的 1 MiB 窗口。

局域网结果受同一台主机限制。往返 100 毫秒的结果受 Ubuntu 默认 TCP 缓冲区限制，0.6.0 不修改系统的 TCP 设置。同样的条件下，普通 TCP 大约是 30 MB/s。
