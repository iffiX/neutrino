# The AI module

How the AI gateway behaves: what CLIProxyAPI serves, how a request picks its
upstream, what each panel surface owns, and which names a machine is allowed
to see. The system-level story — metering at the hub, the sealed keys, the
no-backup rule for accounts — is [architecture.md](../architecture.md); this
page is the module's behavior, pinned to the carried binary (7.2.146, probed
live on 2026-09-04).

## What serves

One CLIProxyAPI process per hub, on `listen_port` (default 8317), driven
entirely by the rendered YAML. It listens on `127.0.0.1` alone, so no
exposure and no firewall rule names its port. The hub's own machine reaches
it there. A client reaches it through its own forward and the `connect`
streams the hub relays, and a managed machine through its agent's forward
("How a managed machine's tools are pointed at the gateway"). A container
reaches the same forward at `host.containers.internal`
([../agent.md](../agent.md), "The listeners a container reaches"). A machine on
the LAN with neither a client nor an agent does not reach it. Two kinds of
credential feed it:

- **Providers** — API-key endpoints, stored in `config/ai/providers.json`,
  each keyed by a vault token. The kind names the protocol spoken
  (`anthropic`, `openai`, `gemini`, `custom`), never the vendor behind it.
- **Accounts** — OAuth subscription logins (auth files in the state root,
  hot-reloaded within ~2 s, never in a backup). Login kinds the binary has:
  `anthropic`, `codex`, `antigravity`, `kimi`, `xai`. There is no Gemini
  OAuth in 7.2.146; Google models arrive by API key, Vertex import, or the
  antigravity flow.
- **Ollama providers**: one per machine whose Ollama runs and holds a model,
  generated by the hub and never stored in `config/` ("Every machine's
  Ollama").

## A key per device as well as per client

A managed device whose AI tools use the gateway has a gateway key of its
own. `config/cliproxyapi/cliproxyapi.json` keeps `device_keys` beside
`client_keys`, sealed the same way, and the renderer writes both lists into
the gateway's `api-keys`. `ensure_device_key`, beside `ensure_client_key` in
`modules/clients/ai_keys.py`, mints a device's key when the first of its
accounts turns its AI tools switch on. The key is revoked when the last one
turns it off and when the device is removed; every account of the device
holds the same key. No module's state holds it: the device's `ai_tools`
section does ("How a managed machine's tools are pointed at the gateway").

A container module that uses the gateway, Hermes WebUI or Ayakaleaf, has a
key of its own on each device. The hub generates it, seals it in that module's
`config/devices/<id>/<module>.json`, registers it under the device and the
module, and voids it at the module's uninstall. The renderer writes it into
`api-keys` beside the keys of `cliproxyapi.json`, reading every such module
file. It does not follow the device's AI tools setting, and the module's
containers receive it in their environment
([../agent/modules/containers.md](../agent/modules/containers.md),
"Reaching the machine"). Its usage is a row of its own, under the device and
the module.

SiYuan, a program run as each enabled account, has a key of its own for each
account it enables. The hub generates it when the account is enabled, seals
it in `config/devices/<id>/siyuan.json`, registers it under the device, the
module and the account, and voids it when the account is disabled or removed
and at the module's uninstall; the renderer writes it into `api-keys` as it
writes a container module's. The agent writes it into the account's own
SiYuan settings, and it does not follow the device's AI tools setting
([../agent/modules/siyuan.md](../agent/modules/siyuan.md), "The gateway").
Its usage is a row of its own under the device, the module and the account.

## How a request routes

1. **The model name picks the upstream family.** A name only one family
   serves goes there; families never compete for a name they do not claim.
2. **Inside a family, every credential is one pool.** Accounts and API-key
   providers deduplicate into the pool and rotate round-robin; the only
   ordering hook is a per-credential `priority` (default 0, not surfaced in
   the panel). A credential that fails is marked (`failed`, `unavailable`,
   `quota` — the account row's status dot) and the rotation skips it.
3. A name nothing claims is refused: `400 unknown provider for model`.

The Providers panel's list order is the serving order **among API-key
providers**; it does not rank accounts against them, and the panel says so
in one hint sentence rather than pretending to a cross-kind ordering the
binary does not have.

## Names are the gateway's to define

The gateway is the single namespace for model names. A provider record's
`models` list maps upstream names and may alias them (`real = alias`), and
what `/v1/models` then shows **is** the catalog every machine sees. A device
never invents a name; its tools pick from the gateway's list.

An alias that collides with a name an account already serves joins that
name's pool and rotates with it — so borrowing a family's real names for
another upstream is only clean while no account of that family is signed in.

Client menus (Claude Code's `/model`, Codex's picker) enumerate their own
built-in slots, not the gateway's catalog. A slot's meaning is remapped in
the tool's configuration (Claude Code: `ANTHROPIC_MODEL` and the three
`ANTHROPIC_DEFAULT_*_MODEL` variables; Codex: profiles), and any
gateway-listed name can be used past the menu by spelling it out
(`--model`, `/model <name>`). Which gateway names a machine's slots map to
is the tool configuration the switch writes: the client's **Configure**
dialog on a person's computer, the account's form on the machine page on a
managed machine.

## The served list

The served list is the last set of names the gateway's `/v1/models`
returned with at least one name in it, and empty once no credential feeds
the gateway. The hub probes the gateway at most
once in 10 seconds, and every page of this standard that names the
models the gateway serves means this list. Its readers are SiYuan's
`models`, the AI tools' setting, the default model ("The default model"),
and the model pickers of the machine page. The `ai` entry of the published list holds no model
while the gateway's unit is stopped. The probe line on Activity and the
**Default model** picker of Access read a probe of their own at each read
of the page.

| Rule | Reason |
| --- | --- |
| A probe that fails or returns no name leaves the list as it was while an account is signed in or a provider is turned on. The list is empty until a probe first returns a name. | The probe returns no name while the gateway restarts or is stopped. A list that empties and comes back is two changes for every reader: each SiYuan instance stops and starts twice, Ayakaleaf's app restarts twice, and every account's AI tools are switched back and then to the hub again. |
| A probe that fails or returns no name empties the list while no account is signed in and no provider is turned on. The hub reads both from its own files: a token file in the gateway's auth directory under the state root, and a provider in `config/ai/providers.json` turned on with a key or a generated provider in `cliproxyapi/ollama_providers.json` under the state root ("Every machine's Ollama"). Each reader follows the empty list once. | The names of a signed-out account and of a provider turned off no longer work, and SiYuan, Ayakaleaf and the AI tools would go on calling the hub with them. A probe returns no name both while the gateway restarts and after the last credential goes, and the hub's own files tell the two apart. |
| A probe that returns another set of names replaces the list, and each reader follows it once. | An account signed in or out, a provider turned on or off, and a new catalog in the gateway's binary each change the names the gateway serves. |
| The hub stores the list in `cliproxyapi/served_models.json` under the state root, writes it when the list changes, an emptied list included, and reads it at the panel's start. | A reboot or a hub update starts the panel and the gateway together, and a machine that reconnects before the gateway first returns a name gets the stored list in its state. The list is what the gateway last served and no person's decision, so it stays out of `config/`. A restored box probes the gateway again. |

## Every machine's Ollama

Every program that reaches the gateway can use the models of every
machine's Ollama ([../agent/modules/ollama.md](../agent/modules/ollama.md)),
as it uses a cloud provider's. The hub generates one OpenAI-compatible
provider per machine whose Ollama runs and holds at least one model, and the
gateway's render writes each beside the stored providers.

| Rule | Reason |
| --- | --- |
| A machine has a provider while its agent's session is live, its Ollama row reports `is_running`, the hub holds its forward to Ollama's port, and `GET /api/tags` lists at least one model. The provider's address is that forward, `http://127.0.0.1:<port>/v1`, and its models are the names `/api/tags` returns. | The forward is the hub's one way to the machine's port (ollama.md, "The model list is the hub's, through a forward of its own"). Ollama serves the OpenAI chat API under `/v1` with no setting. |
| A model's name is Ollama's own, with no machine name in front. The same name on two machines joins one pool and rotates round-robin, as the credentials of one family do ("How a request routes"). | A tool asks for `qwen2.5:7b` whichever machine runs it, and a second machine with the same model shares the requests. |
| The renderer writes a generated provider as an `openai-compatibility` entry named `ollama-<device id>`, with no `api-key-entries`, after the stored providers. | Ollama's API takes no key, and 7.2.146 serves an entry with none. A probe of the binary on 2026-11-14 listed a name of two such entries once in `/v1/models`, rotated requests between them, skipped one at a closed port, and translated the Messages and Responses formats to Ollama's chat API. |
| The hub never writes these providers into `config/ai/providers.json`. It stores the generated list in `cliproxyapi/ollama_providers.json` under the state root, `{providers: [{device_id, address, models}]}`, and every render reads it, the panel's and `nhub apply`'s alike. | The list is what the machines last reported and no person's decision, so it stays out of `config/` and out of a backup. A render reads only files, and a render without the list drops every machine's models until the list next changes. |
| A change of the list is written into the served file in place, as a change of keys is, and the gateway reloads it within a second. The reload also serves the stored providers as they stand. | The list changes each time a machine comes or goes, and a restart cuts every request in flight. |

The hub reads `/api/tags` through the machine's forward, on a thread of its
own, at these events:

| Event | What the hub does |
| --- | --- |
| A report that says the machine's Ollama runs while the hub follows no provider of it: the module's first **Start**, an Ollama found running, the machine back online | reads `/api/tags` and adds the provider |
| A report after the forward started again at a new port | reads `/api/tags` and writes the new address |
| A pull ending in success, a **Remove** on the machine's Models panel | reads `/api/tags` for that machine again |
| Every 30 seconds | reads `/api/tags` for every machine it follows |
| The machine's session ending, a report that says its Ollama does not run (a **Stop**, an **Uninstall**), the machine leaving the hub or removed | takes the provider out at once, with no read |
| The panel's control connection to the transport closing, at a transport or panel restart, which the panel counts as every session ending | takes nothing out, and follows no machine until its next report |
| `/api/tags` listing no model | takes the provider out |
| A read that fails | keeps the provider as it was, at the forward's address now |

| Rule | Reason |
| --- | --- |
| The read runs every 30 seconds. | It finds a model pulled or removed on the machine itself, with `ollama pull` or `ollama rm`, within half a minute, and each read is one small request over the machine's channel. A pull or a removal on the Models panel moves the list at once. |
| A forward lasts while the transport's control connection that started it is open, so a transport or a panel that restarts leaves every forward's port dead. The providers stay, at the panel's start too. At the new control connection each machine's next report, at most 5 seconds later, starts its forward again at a new port, and the hub writes the new address. The names stay, so the served list does not move. Until then a request for a name another machine also serves goes to that machine, and a request for a name this machine alone serves fails. | The gateway skips a provider it cannot connect to and tries the next one of the pool. A list emptied at a restart takes every local name out of the served list and brings it back seconds later, two changes for each reader. A transport restart in the lab did that within one second. |
| The first 30-second read after a new control connection comes 30 seconds after it, and takes out the provider of every machine that has not reported its Ollama running by then. | Agents report every 5 seconds. A machine that left while the panel was stopped has its provider taken out at that read. |
| An agent that stops ends its session at once. A machine taken off the network keeps its provider until its session ends, at most 80 seconds later, `KeepAliveInterval` and `KeepAliveTimeout` ([../transport.md](../transport.md), "The timings"). | A machine is online while its session is live, everywhere in the hub. |

The served list follows these providers as it follows a provider turned on
or off ("The served list"). A name that leaves the gateway leaves the list
at the next probe, at most 10 seconds later, and each reader follows once.
It comes back the same way with its machine. A generated provider counts as
a provider turned on with a key. While one is stored, a probe that fails
leaves the served list as it was, and the last one going while no account
is signed in and no other provider is turned on empties the list once.

The **Providers** panel of the AI page draws each generated provider as a
read-only row, read with `GET /api/hub/ai/ollama`
([../ui_behavior.md](../ui_behavior.md), "The Ollama rows of the Providers
panel"). Its models are pulled and removed on the machine's Models panel,
which the row links to. No frame, stream kind or agent command is added for
this, and the agent changes nothing: its report and the forward of
ollama.md carry it.

## The default model

The default model is the model every tool and app of the hub uses where
nobody chose one. A person picks it in the **Default model** picker of the
Access panel ([../ui_behavior.md](../ui_behavior.md), "The Access panel of
the AI page"), and the hub keeps the pick as `default_model` in
`config/cliproxyapi/cliproxyapi.json`, empty until a person picks one. Its
readers are the unchosen models of the AI tools, on a managed machine and on
a client; Ayakaleaf's model while its tab names none; Hermes WebUI's `model`;
and SiYuan's `model`.

| Rule | Reason |
| --- | --- |
| The default model is the pick while the served list holds it, and otherwise the first name of the served list, which is sorted by name. It is empty while the list is empty. | The gateway rejects a request that names a model it does not serve with `400 unknown provider for model`, and a provider turned off or an account signed out takes its names out of the list. |
| A pick the gateway no longer serves stays in the file, and the picker shows it until a person picks another. | The pick is in force again when its name comes back, as when its provider is turned on again. |
| The pick is written by `POST /api/hub/ai/gateway/set {default_model}`, which restarts nothing. The hub then sends its state to every online machine and client whose state changes, a client's through its `ai` entry, which carries the default model; a client sends its `service` frame again at each state ([../protocol.md](../protocol.md), "The service frame"). | The gateway serves every name the same with any pick. What changes is the model the readers are sent. |
| A model chosen for one account's tool, or in one Ayakaleaf tab, stays. | The default model fills only what nobody chose. |

## What each panel surface owns

| Surface | Owns |
| --- | --- |
| Activity | Status dots, today's counters, the probe line (`/v1/models` as served), journal, and the chip-switched usage tables |
| Providers | API-key provider records, their aliases, their serving order, enable/disable — staged behind the panel's apply, with the gateway-behind signal; and a read-only row for each provider generated from a machine's Ollama ("Every machine's Ollama") |
| Accounts | Subscription sign-in (redirect flows finish by pasting the dead callback page's address; device flows show a pairing code; a timeout keeps the dialog open, [../ui_behavior.md](../ui_behavior.md), "Account sign-in on the AI page"), status, revocation — immediate, never staged |
| Access | Keys for a tool on the hub's machine or one using an SSH tunnel to it, plus the endpoint line, which names the gateway on the hub's loopback, and the default model, staged behind the panel's apply while a key's generate and revoke write at once; a managed device is keyed when the first of its accounts turns its AI tools switch on, on the machine page, and its key reaches it over the agent channel. The hub holds a key of its own beside them, minted on the first apply and shown nowhere: it is what the hub probes `/v1/models` with, and it keeps the gateway's key list from ever being empty, since CLIProxyAPI with no key configured asks nobody for one |
| Gateway port | `listen_port`, staged behind its own apply |

## How a client points its tools at the gateway

The client does not write a tool's configuration itself. It hands the hub
to cc-switch as one more provider and lets cc-switch write Claude Code's
`settings.json`, Codex's `config.toml`, Gemini's `.env` and OpenCode's
`opencode.json`, in each tool's own format. What the client owns is the order of operations, because
cc-switch replaces a tool's file whole when it switches and would otherwise
drop what the person had in it.

The endpoint a tool is given is the client's own local port,
`http://127.0.0.1:<local-port><path>`, `<path>` being the path of the `ai`
entry's `endpoint`, empty for the endpoint the hub publishes. The client listens there while it runs and the
hub is the exit of any tool, and sends each connection to the gateway as a
`connect` stream ([../protocol.md](../protocol.md), "The connect stream").
The key is this client's own gateway key from the `service` frame, and the
gateway checks it on every request. A tool works only while the client
runs, and the client's AI page says so ([../client.md](../client.md), "The
AI page").

Before the hub is ever made current for a tool, the client hands cc-switch
what the person already had, through cc-switch's own stores:

| Step | cc-switch command | What it keeps |
| --- | --- | --- |
| List | `provider list` | cc-switch takes a configuration it has never seen into its store as the provider `default`, which is what switching back returns to |
| MCP servers | `mcp import` | The tool's live MCP servers, which cc-switch then writes into every configuration it makes |
| Shared settings | `config common extract` on the live file, then `config common set` | Claude's `permissions`, `hooks`, `statusLine`; Codex's `approval_policy`, `sandbox_mode`; Gemini's own variables |
| The hub | `provider add --common-config` with the endpoint, key and model flags, then `use` | The hub's provider carries the shared settings, so both stand in the file at once |

Of these steps OpenCode takes the list and the hub alone. cc-switch
5.10.4 adds a provider to OpenCode's `~/.config/opencode/opencode.json`
beside every provider and setting the person has there, and keeps no
current one, so nothing of the person's has to pass through its stores:

| Step | cc-switch command | What it writes |
| --- | --- | --- |
| The hub | `provider add --config` with the whole provider, `{npm: "@ai-sdk/openai-compatible", name, options: {baseURL, apiKey}, models: {<model>: {name}}}`, then `use` | `provider.neutrino` in the file, every other key's value as it was |
| Switching back | `provider delete` | the file without `provider.neutrino` |

| Rule | Reason |
| --- | --- |
| The hub's provider names one model, the tool's model. | OpenCode starts on the file's own `model` when it names one, then on the last model it used of a provider it still has, then on a model of a provider the file names. A person with no OpenCode settings of their own starts on the hub's model. |
| The provider goes in whole as `--config`. | cc-switch 5.10.4 refuses `--base-url`, `--api-key` and `--model` for OpenCode: "provider add for opencode requires raw config via --config or --config-file". |
| For OpenCode the hub is current while cc-switch lists its provider. | `provider current` fails for OpenCode, with "Current provider '' not found". |
| A file cc-switch cannot read as JSON fails the switch. | OpenCode accepts comments in `opencode.json`, and cc-switch refuses a file holding one. |

A common snippet the person already set is never replaced. cc-switch's
extract counts the provider's own model as shared for Gemini (`GEMINI_MODEL`)
and, defensively, Codex (`model`); the client takes those keys out of the
snippet before saving it, or the snippet would override the hub's choice.

Two things stay the client's own. Codex's reasoning effort has no flag in
cc-switch's `provider add`, so a chosen effort is set as a top-level key of
`config.toml` after the switch. And cc-switch's `provider delete` asks
`(y/N)` on its terminal with no flag in the prompt's place, so the client
runs it on a terminal of its own (a pty on Linux, a pseudo console on
Windows) and answers `y`.

The client records, per tool, which provider was current before the hub,
whether the tool had a configuration file and a directory at all, and the
bytes of every file a switch may write as they were before the first
switch, or that the file was absent: Claude Code's `~/.claude/settings.json`,
Codex's `~/.codex/config.toml` and `auth.json`, Gemini's `~/.gemini/.env` and
`settings.json`, and OpenCode's `~/.config/opencode/opencode.json`. The
record is `{is_present, is_dir_present, kept, kept_modes, previous, added}`,
`kept_modes` being each kept file's own mode outside Windows and `added` the
provider settings last written, and OpenCode's also holds
`is_parent_present`, whether `~/.config` was there. A tool whose
record says it already carries the wanted settings is not run again, so
nothing runs when nothing changed.

cc-switch writes a tool's files only into a directory that is there, and
says nothing else when it skips one, so a switch makes the directory of a
tool that has none, and every tool named as switched has its file read back
naming the hub: Claude Code's endpoint, key and model, Codex's, Gemini's
and OpenCode's endpoint. cc-switch writes those files with the person's own
file mask, so every file that then holds the gateway key, Claude Code's
`settings.json`, Codex's `auth.json`, Gemini's `.env` and OpenCode's
`opencode.json`, is set to mode 600 outside Windows. Deactivating switches back to the recorded provider, deletes the
hub's entry, then writes each kept file back byte for byte with its own
mode, takes away each
that was absent, and takes away a directory the switch made once it is
empty, OpenCode's `~/.config` among them; cc-switch's own switch back re-writes a file in its own layout, so
its result is never what is left. A switch back that cannot run cc-switch,
or cannot read its list of providers, fails and keeps the records, so the
person's own files are still there to put back at the next try. What the
adoption imported into cc-switch's MCP store and common snippet is in a
store of the client's own: every cc-switch the client starts has
`CC_SWITCH_CONFIG_DIR` set to `cc_switch` under the client's own directory,
mode 700, so the person's `~/.cc-switch` and the CC Switch app that keeps
its store there are never read or written, and deactivating removes that
store. A tool's record says `is_own_store`; a tool switched before the
store existed is switched back in `~/.cc-switch`, where it was switched.

## How a managed machine's tools are pointed at the gateway

A managed machine's AI tools are pointed at the gateway by the steps of the
client's section above, run by the agent: the same cc-switch, the same
commands in the same order, the same record per tool, the same switch back.
This section states only what differs, so the two cannot drift.

The setting is one per available account of the machine, in the account's
form on the machine page ([../agent.md](../agent.md), "The two layers and the
accounts"): whether that account's AI tools use the gateway, and the
account's tool configuration (`{claude: {default, opus, sonnet, haiku},
codex: {model, model_reasoning_effort}, gemini: {model}, opencode:
{model}}`), each model
picker's first choice being the gateway's default. It is off on a new
account. The hub keeps it on the account's row in
`config/devices/<id>/accounts.json` and sends it in the device's `ai_tools`
section ([../protocol.md](../protocol.md), "The
sections").

| | On a person's computer | On a managed machine |
| --- | --- | --- |
| Who runs the steps | the client | the agent |
| As whom | the person, in their own session | each account the hub names, never root or SYSTEM: `runuser -u <account> --` on Linux, a process with the account's uid and groups on macOS, a one-shot scheduled task under the account's login on Windows ([../agent/ai_tools.md](../agent/ai_tools.md)) |
| The accounts | the person's own | every available account whose switch is on, sent in the state with its own tool configuration |
| The endpoint | `http://127.0.0.1:<local-port><path>`, the client's forward | `http://127.0.0.1:8317`, the agent's own forward, which relays each connection to the hub over the agent's channel ([../agent.md](../agent.md), "The AI gateway forward"); on the hub's own machine `http://127.0.0.1:<listen-port>`, the gateway itself |
| A tool works | while the client runs and its channel to the hub is up | while the agent runs and its channel to the hub is up |
| The key | the client's own, from the `service` frame | the device's own, from the `ai_tools` section |
| The unchosen models | the default model ("The default model"), from the `service` frame | the default model, filled in by the hub before the state is sent |
| The cc-switch | the copy the client's package carries | the copy the agent fetches from the hub into `ai_tools/bin/` under its state root, the same pinned version |
| The record per tool | `original/<tool>.json` under the client's configuration | `ai_tools/<account>/<tool>.json` under the agent's state root, never in the account's home ([../agent/ai_tools.md](../agent/ai_tools.md)) |
| Switched back | when the chip goes off | when the account's switch goes off, when the account is removed from the machine page, before `nagent service uninstall`, and when the machine leaves the hub |

cc-switch runs on a store of the agent's own in the account's Neutrino
tree, as the client's runs on a store of the client's own, so the
account's `~/.cc-switch` is never read or written ([../agent/ai_tools.md](../agent/ai_tools.md)). An account whose switch turns on is
switched at the next state. While the served list is empty ("The served
list"), the hub sends the setting as off, so every account is switched back;
the stored setting and the device's key stay, and the next state after the
list holds a name switches the accounts back to the hub. Codeg's Claude Code and Codex
entries are the ACP adapters `claude-agent-acp` and `codex-acp`, which read
the same files cc-switch writes, so the setting covers Codeg's sessions
([../agent/modules/codeg.md](../agent/modules/codeg.md)).

A desktop client on a managed machine leaves its AI page to the agent
([../client.md](../client.md), "The AI page"), because both would write the
same tools' files with different endpoints.

## Metering

The panel drains the management API's usage queue (a destructive pop; the
collector is the only reader) into per-key × per-provider cells — days kept
forever, hours 48 h, minutes 90 min. `failed` counts upstream failures only:
a request refused before reaching a provider (bad name, bad client key) is
never queued. Token fields are the vendor's own accounting — `input_tokens`
includes what the cache served, so a cache share is `cache_read / input`.

Usage is counted per key id, so a device key is a row of its own in the AI
page's usage table, beside each client's.

The management key that unlocks the queue is machine-generated, sealed under
the vault's data key beside the module's config, working copy in the state
root; it is deliberately not a user-facing credential, so no cascade delete
can switch metering off.
