# Tests

Seven blocks of tests, split by what they may touch. The **agent**,
**client**, **hub** and **go** blocks run in-process in milliseconds and
touch nothing outside their own temporary directories. The **android** and **ios** blocks run the
apps' unit tests on the build machine, with the phone's system services faked.
The **integration** block runs on live machines in the CI/CD release pipeline
and touches everything, because the seams it exists for (package managers,
systemd, wires between two machines) are exactly what the in-process blocks
fake.

| Block | Lives in | Runs | May touch |
| --- | --- | --- | --- |
| agent | `agent/tests/` | `pytest -q` on pytest-xdist workers, seconds, every commit | Fakes and `tmp_path` only: fake platforms, injected clocks, sockets on temporary paths; an autouse fixture redirects every store off the real machine |
| client | `client/desktop/tests/` | `pytest -q` on pytest-xdist workers, seconds, every commit | Fakes and `tmp_path` only: fake platforms and toolkits, the compiled and fetched parts stood in for |
| hub | `hub/tests/` | `pytest -q` on pytest-xdist workers, under a minute, every commit | FastAPI test clients and temporary config roots; never a unit, an interface, or `/etc` |
| go | `transport/` and `agent/sshserver/`, each test beside its file, and `transport/tests/` | `go vet ./...` and `go test -race ./...` in each module, in the `go` job of `ci.yml`, every commit | sockets on loopback and temporary directories alone; the Python side of every local channel faked by a test that speaks its lines |
| android | `client/android/app/src/test/` | `./gradlew test lint`, every commit | JUnit on the JVM; a fake socket, fake Keystore and fake VpnService; never an emulator or a device |
| ios | `client/ios/NeutrinoTests/`, `client/ios/NeutrinoUITests/` | `swift-format lint --strict --recursive` and `xcodebuild test` on the iOS Simulator, in the `ios` job of `ci.yml` on GitHub's `macos-15` runner, every commit; the `ios_core` job builds the app for a device with the RustDesk core, checks the app defines `_nd_attach_frames`, and keeps the unsigned `.ipa` as the run's artifact `client_ios_device_test` for a test on an iPhone | XCTest; a fake socket, a fake Keychain, a fake SMB client and a fake RustDesk core; never a device |
| integration | `packaging/integration/` | `run_on_box.sh` on the pipeline's VM pair; minutes | A whole machine: real installs, real systemd, real DHCP on a served wire, a real client VM |

The `conftest.py` of the agent, client and hub blocks has two guards. A
process guard fails a test on any program that changes the machine or asks
for authorization, such as `systemctl`, `nft`, `apt` or `sudo`. An audit hook
fails a test that writes, creates, renames or removes a file outside its
temporary folders. Its failure message names the path and the test. The agent
block's `conftest.py` ends the reads of each reconcile worker and the start
watch of each engine at the end of its test.

## Parallel runs

The hub, agent and client suites run on pytest-xdist workers, as
`pytest -q -n <workers> --dist loadgroup`, in a checkout and in `ci.yml`.
pytest-xdist comes with the hub's dev extra, and the jobs that install pytest
by name install it beside. A suite run without `-n` runs in one process and
passes the same.

Most of a hub or agent test's time is a wait on a subprocess, a socket or a
timer, so those suites still gain from more workers than processors. A
machine of 16 processors runs a suite on 16 workers, or on 8 when two suites
run side by side. A runner of `ci.yml` has 4 processors and runs the hub's
and the agent's suites on 8 workers, and the client's on 4: its tests spend
their time in Python, the more so under the coverage tracer.

`--dist loadgroup` hands each test to the next free worker on its own, and
the tests marked with one `xdist_group` to one worker in their order. A group
saves work and no test's result rests on one: pytest-xdist 3.8 cannot name a
group under pytest 9.2, and the marks then do nothing. The packaging files
whose first test draws the icons the rest reuse carry one each. The agent's
two tests of a reconcile worker left running carry one, and the second runs
both in a process of its own when the first ran in another.

A test that runs beside tests in other processes holds to these rules:

- It takes a port the system picks, or searches from a random port; it never
  starts from a fixed number.
- A socket path it makes stays under the system's limit, whatever the folder
  of its worker.
- An order of events it proves is held by an event or a fake clock, never by
  a time the other side has to finish in.
- No thread it starts outlives it.
- A function of `os` or `time` it replaces still serves every other caller,
  the coverage tracer and the other threads of its process among them; the
  block's `conftest.py` gives `own_sleep` for a `time.sleep` that records the
  test's own waits.
- A state it hands to the next test still holds when the two run in
  different processes.

## Python 3.9

The agent's source declares Python 3.9, the oldest a checkout runs it on. A
newer Python takes what 3.9 rejects: syntax newer than 3.9, a union written
`X | Y` in an annotation evaluated as its module loads, and names of the
standard library newer than 3.9, such as `zip(strict=)`, `tomllib` and
`datetime.UTC`. Syntax and such an annotation fail the import of their module,
a newer name only the code that runs it.

The `agent_oldest_python` job of `ci.yml` runs the whole agent suite on 3.9.
A checkout runs on 3.9 `pytest -q --collect-only`, which imports every test
file and the packaging scripts they load, then `tests/test_imports.py`, which
imports every module of the package, and the test files of the code a change
touches.

## The mirror rule

Where a source file is testable on its own, its tests live in the file that
mirrors it: `agent/neutrino_agent/<package>/<module>.py` is tested by
`agent/tests/<package>/test_<module>.py`, and the hub tree likewise: a router
in `hub/neutrino_hub/web/routers/{hub,agent}/<page>.py` is tested by
`hub/tests/web/routers/{hub,agent}/test_<page>.py`; the agent's
`modules/shared/` is mirrored by `tests/modules/shared/` and
`modules/remote_desktop/rdp/` by `tests/modules/remote_desktop/rdp/`. Every
test directory carries an `__init__.py` so mirrored names never collide,
and the shared fakes (the fake platform, the injected clock, the redirect
of every store into `tmp_path`) are in the block's `conftest.py`, never
copied into files.

A scenario that crosses files lives with **the surface the operator
touches**: `sudo nagent status` asking a live in-process control server is
`cli/test_status.py`'s case, not the server's, because the thing under test
is what the person typed. The server file keeps the route-level matrix; the
cli file keeps the operator's walk.

## Editions

The hub and the client blocks run twice in CI: on the full tree, and on the
mainland tree that `build_sources.py --edition cn` writes, where both run
their whole suites and the frontend runs `npm run build`. A checkout runs the
mainland tree's hub suite. The agent's files are the same in both trees and
none of its tests reads a file the mainland tree changes, so the agent block
runs once.

The mainland tree runs the hub's whole suite. A choice of the tests its
edition files can change keeps the tests that read the stamped install
scripts, which are among the slowest. A rule by text or imports that keeps
every test reaching the edition table keeps nearly every file, and a smaller
rule leaves out tests that reach the table through another module.

A test that needs a left-out feature lives in that feature's own mirrored
directory and is deleted with it. A test outside that directory that needs one
carries `@pytest.mark.feature("<name>")`, and the block's `conftest.py` skips
it when the edition table reports the feature absent
([architecture.md](architecture.md), "A left-out feature is reached through
one table"). The edition table's own test, `hub/tests/test_edition.py`, reads
every Python file of the hub and fails on an import of a left-out package from
outside that feature's files and the table.

## Coverage

The `python` job of `ci.yml` runs the hub's and the agent's suites, and the
`client` job runs the client's. Each suite runs with `--cov` over its own
package (`neutrino_hub`, `neutrino_agent`, `neutrino_client`) and writes
`coverage.xml` in its block's directory. The `agent_oldest_python` job and the
mainland jobs run their suites without coverage.

`codecov/codecov-action` uploads each file to Codecov under the flag `hub`,
`agent` or `client`. It signs in with the job's GitHub OIDC token, which needs
`id-token: write` on the job. Each upload's `network_filter` names its
package's directory, because the three packages share file names such as
`cli/entry.py`.

The same three files go to Codacy, each with `--partial` and its block's
directory as `--prefix`, and the job `coverage_final` sends `final` after both
jobs pass. With no `CODACY_PROJECT_TOKEN` secret, `--skip` passes over them,
and a failed upload leaves its job green.

A job passes or fails on its tests alone, whatever its coverage. pytest-cov
comes with the hub's dev extra, and the `client` job installs it by name
beside pytest.

## The integration block

Flat, one file per concern, because these mirror machine states rather than
source files. `run_on_box.sh` orders them: install, footprint, reinstall,
reset, set up again, a module install through the panel, the whole-page

only two live machines can prove: the control channel answering each

stderr arrives apart from its stdout.

`packaging/ci/check.py` runs on every built package in the release
workflow. Its `hub_macos` check, on both macOS architectures, and its

stopped, run `nhub setup --json` with the answers of a `server` hub that
installs its local agent, and expect the panel to answer
`http://127.0.0.1:8080/api/hub/display` with 200. They then stop the hub,
remove it, and run `install.sh` or `install.ps1` with `NEUTRINO_ASSET_DIR`
naming the built files, up to `nhub --version`. `hub_windows` also reads the
hub's rules in Windows Firewall: `neutrino_hub_setup` while the wizard
serves, `neutrino_hub_panel_http` and no `neutrino_hub_setup` after setup,
and no rule of the hub's after the removal. Its `agent_windows` and
`client_windows` checks first install the released 0.4.0 `.msi` pinned in
`packaging/shared/constants.py` and the built one over it, so every build
runs an upgrade's whole sequence. That one install may end in 3010, a
restart owed because 0.4.0's removal does not wait for its services; the
check accepts it, removes the package, takes the files of ours waiting for
the restart off Windows' list, and then installs the built `.msi` on a clean
machine, where no restart and no file waiting for one is accepted. An
upgrade from 0.4.0 is not otherwise supported. The hub has no Windows
package before 0.5.0, so `hub_windows` installs on a clean machine.

receipt. It starts no machine.

## What a change owes

A new module, service type, route, CLI verb or Go file arrives with its
mirrored test file in the same commit, and every new test holds to the rules
of "Parallel runs". A new operator-visible behavior adds its cell to
the cli or control matrix. Changing a channel model fails the golden schema
test until `PROTOCOL` moves or the change is shown additive
([protocol.md](protocol.md), "Versioning"). A new `{code}` anywhere adds its
word to the page's table, which the completeness assertion enforces. The pipeline gains a case only when
the behavior needs a real machine to exist.
